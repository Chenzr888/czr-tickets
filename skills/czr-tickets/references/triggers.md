# 什么时候让 AI 去处理

三种方式，可以同时用。接入时问用户想用哪种，推荐先用第 1 种试，顺手了再上第 2 种。

## 1. 定时看一眼（最简单）

在 AI 对话里说：`/loop 10m 处理工单` —— 每 10 分钟处理一轮。对话窗口开着才会跑，适合白天边干活边让它盯着。

## 2. 来单就处理（事件驱动）

在项目根目录开一个终端窗口，常驻运行：

```
node <技能目录>/scripts/watch.mjs <跑一轮的命令>
```

客户一提交、或者你一批复，它就叫 AI 跑一轮。同一时间只跑一轮，卡住的单子不会反复触发。

"跑一轮的命令"按用户用的 AI 来填（接入时问一句他用哪个）：

| 用的 AI | 命令 |
|---|---|
| Claude Code | `claude -p "处理工单" --permission-mode acceptEdits` |
| Codex | `codex exec -s workspace-write -c 'sandbox_workspace_write.writable_roots=["<项目绝对路径>/.git"]' "处理工单"` |
| 其他 | 能"一句话跑一轮、跑完退出"的命令都行 |

无人值守跑的时候 AI 需要能改文件、跑命令、写版本记录（开工作副本要用），所以权限要给够——Codex 默认不让写版本记录，所以上面要单独放开 `.git`，其他保护不变；正因为没人看着，规矩里的"永远不上线、改进单要批复"更重要。告诉用户：这个窗口关了就不盯了，想开机就跑可以让 AI 帮他做成开机自启。

## 3. 接进已有的流程

只要能在某个时刻执行一条命令，就能接：

- **系统定时**：每天早上 9 点跑一轮——把第 2 种里的命令放进系统定时任务（crontab 等）。
- **GitHub**：仓库里有人提 issue 时跑一轮——在 GitHub Actions 里装好 AI 的命令行，触发条件写 `issues: opened`，步骤里先把 issue 内容用 `tickets.mjs new` 记成单子，再跑一轮。改动以待合并的修改提交，由人合并。
- **网站后台**：接口收到新单子后直接执行一轮命令（不想开第 2 种的常驻窗口时）。注意别让并发的请求同时跑多轮。

不管从哪触发，跑的都是同一句"处理工单"，规矩都一样。
